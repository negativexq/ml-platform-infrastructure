# M6 Gate — evidence

Run date: 2026-09-10 · Terraform v1.15.8 · TFLint v0.64.0 · AWS provider ~> 6.0

**No AWS infrastructure was created.** M6 is a design milestone: the platform
validated locally in M0–M5 expressed as code, checked by the same tooling that
would gate a real change. `terraform plan` was not run — it needs credentials,
and this repository holds none.

## Local → AWS mapping frozen

Recorded in [../../aws-architecture.md](../../aws-architecture.md) with a
Terraform module named for each row. The mapping is a contract, not a sketch:
the Helm chart already renders the AWS side of it without template changes.

## Terraform structure

```
infra/terraform/
├── modules/
│   ├── vpc/     public+private subnets, 1 NAT, S3 gateway endpoint
│   ├── ecr/     immutable tags, scan on push, lifecycle policy
│   ├── s3/      encrypted, public access blocked, versioned, lifecycle
│   ├── rds/     private, SG-to-SG ingress only, AWS-managed password
│   ├── eks/     cluster + one CPU SPOT node group + OIDC provider
│   └── iam/     four separate identities
└── environments/
    └── aws-dev/ providers.tf main.tf variables.tf outputs.tf
                 terraform.tfvars.example
```

Every module has `main.tf` / `variables.tf` / `outputs.tf`, every variable a
description, and every module its own `required_version` and
`required_providers` block.

### tflint found a real defect

The first run was not clean:

```
1 issue(s) found:

Warning: Missing version constraint for provider "tls" in `required_providers`
  on infra/terraform/modules/eks/main.tf line 137:
 137: data "tls_certificate" "oidc" {
```

The EKS module reads the OIDC issuer's certificate thumbprint with the `tls`
provider but never declared it, so the module would have resolved whatever
version happened to be around — exactly the unpinned-dependency problem the
rest of the repo avoids. Declared, and the run is clean.

## IAM design documented

Four identities, no shared admin role — detail in
[aws-architecture.md § Identity boundaries](../../aws-architecture.md#identity-boundaries):

| Identity | Assumed via | Permitted |
| --- | --- | --- |
| `github-ci` | GitHub OIDC, one repo + ref | `ecr:PutImage` on one repository |
| `inference` | IRSA | `s3:GetObject` on the artifact bucket — **read only** |
| `mlflow` | IRSA | S3 read/write + `secretsmanager:GetSecretValue` on one ARN |
| node | instance profile | the three managed EKS policies — **no S3** |

Enforced in code, not just prose:

- A variable validation rejects any GitHub subject claim not starting with
  `repo:`, so the CI role cannot be left assumable by any repository.
- The IRSA trust policies pin `sub` to
  `system:serviceaccount:ml-platform:<name>` — one namespace, one
  ServiceAccount.
- The node role attaches exactly three managed policies and no S3 access, so
  workload permissions cannot be inherited by every pod on the node.
- The RDS password is generated by AWS (`manage_master_user_password`) and read
  from Secrets Manager. It is never a Terraform input.

## Network design documented

Public subnets carry the ALB and NAT; private subnets carry nodes and RDS. RDS
takes ingress from the EKS cluster security group only — a security-group
reference, never a CIDR. An S3 gateway endpoint keeps artifact traffic off NAT.
Diagram in
[aws-architecture.md § Network boundaries](../../aws-architecture.md#network-boundaries).

## Cost model documented

[../../cost-model.md](../../cost-model.md) — estimated **~$155–175/month** if
left running, with the honest headline that the EKS control plane plus NAT is
about two thirds of that and does not scale down with usage. Hence: ephemeral
by default, every module configured so `destroy` genuinely works, SPOT nodes,
`db.t4g.micro`, no GPU, a `max_size` ceiling, and an `aws_budgets_budget`
created alongside the infrastructure with forecast alerts at 80%.

The estimates are labelled as list-price estimates, not measured spend, because
nothing has been applied.

## No secrets in the repo

- `.gitignore` covers `*.tfvars` (with `!*.tfvars.example`), `*.tfstate*`,
  `.terraform/`.
- `terraform.tfvars.example` carries placeholders only.
- Argo CD's repository credentials are read from the GitHub CLI at bootstrap
  and written straight into the cluster — see [../m4/gate.md](../m4/gate.md).

## CI

A `terraform` job runs `fmt -check`, `init -backend=false` + `validate` for
every environment, and `tflint --recursive`. It deliberately does **not** run
`plan` or `apply`: no CI credentials exist, so no workflow in this repository
can create billable infrastructure.

## One chart, both environments

```
$ helm template inference helm/ml-platform --values helm/ml-platform/values-aws-dev.yaml
kinds: ServiceAccount ConfigMap Service Deployment ServiceMonitor
Secret count: 0
secretRef count: 0
```

`values-aws-dev.yaml` renders no Secret and no `secretRef`; the ServiceAccount
carries `eks.amazonaws.com/role-arn` instead. The same chart that serves the
local cluster produces the AWS shape from values alone.

## What is still unproven

`validate` checks syntax and type wiring. It does not check that AWS will
accept these resources: quotas, region-specific instance availability, IAM
policy evaluation, and EKS version compatibility are all still ahead. The first
`terraform plan` against a real account should be expected to surface errors —
that is the next milestone's work, not a gap in this one.
